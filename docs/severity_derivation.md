## Method

For each category, sum the number of **distinct** documented ATT&CK
intrusion-sets (`relationship_type == "uses"`, source `intrusion-set--*`,
target `attack-pattern--*`, both endpoints live) across every technique
mapped to that category. Sub-techniques are rolled into their parent via
set union (not summed) before counting, so a group using two
sub-techniques of the same parent is only counted once. The result is
min-max normalized into `[0.10, 1.00]`.

## One deliberate mapping revision

The first pass mapped `ransomware` to only the four ATT&CK Impact-stage
techniques (`T1486`, `T1490`, `T1489`, `T1485`) and it scored *below*
`scanner` — failing the `ransomware > scanner` sanity gate. Root cause:
those four techniques are narrow and destructive-impact-only, while
`scanner`'s techniques (active scanning, service discovery, brute force)
are used broadly across nearly every group in ATT&CK as general
reconnaissance, inflating its distinct-group count.

Per the troubleshooting table in DEV-BRIEF-05a ("category not ranking as
expected → too few techniques mapped → extend the list; do not weaken
the gate"), the ransomware list was extended with three techniques that
are well-documented parts of real ransomware crews' full killchain
(Conti, LockBit, Ryuk-style "hands on keyboard" operations), not just
the encryption payload itself:

- `T1078` (Valid Accounts) — dominant initial-access vector
- `T1021` (Remote Services) — RDP-based lateral movement
- `T1567` (Exfiltration Over Web Service) — double-extortion staging

This is a mapping fix, not a threshold change — the gate itself was left
untouched.

## Runtime contract

`config/severity_weights.json` is committed and read once at process
start by `app/cti/mitre.py`. The scoring module never re-runs this
derivation and never touches the raw STIX bundle. Re-running
`tools/derive_severity.py` against the same pinned bundle produces a
byte-identical `weights` block.

To refresh for a new ATT&CK release: download the new
`enterprise-attack-<VERSION>.json`, pin its SHA-256, re-run this script,
review the diff in this document, and commit both output files.
